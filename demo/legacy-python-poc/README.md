# Spec-Driven Development Package — Demo + Actual Training

Two things live in this repository, sharing the same underlying materials:

1. **A demo you can run live on a technical evaluation call** — narrated talk tracks (a "Demo talk track" section in each module's `README.md`) showing what the course produces, in 3–7 minute segments.
2. **The materials to actually run the course** — participant hands-on steps (a "Hands-on" section in each module's `README.md`) and one real working reference repo.

Every artifact is real: generated by actually running the GitHub Spec Kit CLI and working through the lifecycle, not hand-written to look like session output. **No client name appears anywhere in this repository.**

Scope note: this build currently covers Modules 1–7 (Days 1–3's core lifecycle, quality gates, delegation, and anti-patterns content). Module 8 (Assessment), the capstone feature, and instructor-only materials are deliberately out for now — straightforward to add back when needed.

## The use case

An **equipment health monitoring & maintenance alerts** service for industrial equipment: field sensors report readings, the system evaluates them against per-equipment-type thresholds, and raises maintenance alerts that staff triage and acknowledge. Chosen for genuine, realistic ambiguity — what to do about equipment that goes silent, how to avoid alerting on sensor noise, how to prevent duplicate alerts — which gives every quality gate in the course something real to catch.

## Structure

```
demo/
  README.md                    this file
  review-trail.html            interactive visual map of all 9 commands + 7 modules — open this first
  project/                     the ONE real, working reference repo — final state, all modules applied
  modules/
    01-vibe-coding-vs-spec-driven/    (+ vibe-coding-exhibit/)
    02-governance-and-clarified-spec/
    03-plan-and-tasks/
    04-quality-gates/
    05-review-and-maintain/           (+ flawed-change/, review.md)
    06-multi-agent-delegation/        (+ delegation-transcript.md)
    07-anti-patterns/                 (+ escalation-antipattern/, comparison.md)
```

Each `modules/0N-*/README.md` has two sections: **Hands-on** (participant instructions, with checkpoints against `project/`) and **Demo talk track** (a short presenter script for a sales/eval call). There's one reference repo, not a snapshot per day — `project/` reflects the *final* state, and the artifacts inside it document their own history inline (`spec.md`'s `## Clarifications` section, `plan.md`'s "Plan Review Note", `checklist.md`'s Finding 1, `analyze-report.md`'s findings) so you can see what changed and why at each stage without needing separate frozen copies per module.

## Using this for a technical evaluation call

Open `review-trail.html` (also published as a standalone artifact) and step through it live — one module at a time, Prev/Next or arrow keys, with the real code/diffs/checklists for each module and a full command reference (all 9 `/speckit.*` commands, with GitHub Copilot and Claude Code usage examples) up front. For a narrated version to read from instead of click through, each `modules/0N-*/README.md` has a "Demo talk track" section — 5–6 minutes for Module 1, 3–7 minutes for the rest. None of it requires live-generating anything; everything referenced already exists and runs.

## Using this to actually run the course

Participants build their own working repo starting in Module 1 (empty, from scratch) and carry it forward themselves through Modules 1–7 — `project/` is the reference answer key throughout, not something copied into participants' hands. Each module's `README.md` has inline checkpoints against `project/` so participants can verify progress without waiting until the end of the day.

## What actually happened across the seven modules (for orientation)

- **Module 1**: A naive one-shot prompt produces real, working-looking code with a permanently dead endpoint and an uninvited SMTP integration (`vibe-coding-exhibit/`).
- **Module 2**: A real Spec Kit scaffold, constitution, and clarified spec — clarify resolves two genuine ambiguities on the record.
- **Module 3**: A plan gets reviewed and corrected, not just accepted.
- **Module 4**: A checklist catches a real missing requirement, an analyze pass catches a real contract inconsistency, one user story gets implemented and tested for real.
- **Module 5**: A candidate follow-up change passes a full green test suite (12/12) while silently corrupting data — caught only by human review against the constitution. That finding produces a real constitution amendment (v1.0.0 → v1.1.0).
- **Module 6**: A second agent instance gets a real delegated implementation task and does genuinely good work — an independent reviewer still finds a concurrency gap it didn't self-report.
- **Module 7**: The same small feature written as an under-specified one-liner and an over-specified pseudo-implementation produce, respectively, silently-invented behavior and a scope violation smuggled past review.
