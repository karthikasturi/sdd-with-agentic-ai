The 9 Commands

Every module ahead exercises one or more of these. Framed around why you'd reach for each one, when, and what you get back — plus how to actually invoke it in GitHub Copilot and Claude Code.

/speckit.constitutionGovernance
Use forSetting ground rules so the agent doesn't quietly make architectural or style decisions on its own.
WhenOnce, right after you initialize the project — before touching any feature.
ExpectA constitution.md that acts like a standing policy doc. Every later command silently checks its output against this. Skip it and expect inconsistent decisions across features — REST here, GraphQL there; strict typing in one place, loose in another.
GitHub Copilot
/speckit.constitution Establish test-first development, explicit rejection of invalid input, and consistent field naming as non-negotiable principles
Claude Code
/speckit-constitution Test-first, explicit rejection of invalid input, no bare except blocks (exact command name depends on CLI version — hyphenated as a skill, or dotted as a legacy slash command)

WhenAt the start of each new feature or unit of work.
ExpectA spec doc with scope, user scenarios, and success criteria — no tech stack mentioned yet. Also a new git branch and folder for the feature. Outcome quality here determines everything downstream — a vague spec produces a vague plan.

Use forSurfacing the ambiguities you didn't realize were in your spec, before they turn into wrong code.

ExpectUp to ~5 pointed questions (“should deleted items be soft- or hard-deleted?”, “what happens on concurrent edits?”). Your answers get written back into the spec. Run it more than once on a gnarly feature — each pass tends to catch different gaps.

Claude Code

Use forBreaking the plan into small, ordered, independently reviewable units of work.

/speckit.analyzeAnalyze
Use forA final consistency sweep — does the spec, plan, and task list actually agree with each other and with the constitution?
WhenAfter tasks, before implement. This is the last cheap point to catch problems — fixing a mismatch here costs a doc edit; catching it after implement costs a code rewrite.

spec.md: Clarifications — asked and answered on the record

Should equipment going silent raise its own alert?

Yes — an “equipment offline” warning after 60 minutes of no reading.

Does one bad reading trigger an alert, or does it need a pattern?

Critical: immediate. Warning: 2 consecutive readings, to filter sensor noise.

EARS format — how every requirement in this course's specs is written

WHEN <a trigger occurs>, THE system SHALL <response>
IF <a condition holds>, THEN THE system SHALL <response>
FR-004WHEN a sensor reading is submitted for an equipment identifier that is not registered, THE system SHALL reject the reading with an explicit error rather than storing it.
FR-007IF a reading's value crosses the equipment type's critical threshold, THEN THE system SHALL create a critical-severity maintenance alert immediately.

Same feature — alert escalation — specified three ways

Under-specified
  • A 15-minute timeout nobody chose becomes load-bearing
  • Applies to every open alert, not just critical
  • No AlertEvent recorded — silent audit-trail gap
Over-specified
  • Raw SQL, bypassing the ORM every other endpoint uses
  • An unvetted scheduler dependency, never run through plan.md
  • Reintroduces a paging integration this spec already ruled out of scope
Corrected
  • States trigger + effect + boundary — critical-only, 30 min, one-time
  • Leaves how — library, schedule — entirely to plan.md
  • Inherits the existing out-of-scope boundary instead of re-litigating it

Hands-on, this module

  1. 1Predict what an under-specified version will get wrong.
  2. 2Predict what an over-specified version will smuggle in.

2 antipatterns Resolved · corrected version shown
modules/07-anti-patterns/escalation-antipattern/

Both directions smuggle a decision past review — one by omission (an implementer fills the gap silently), one by disguise (a “spec” that's really an unreviewed implementation plan).

Over-specification isn't safer than under-specification — it just fails later, and more expensively.
